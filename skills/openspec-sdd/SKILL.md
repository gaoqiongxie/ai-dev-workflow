# OpenSpec SDD 工作流指南

## 概述

OpenSpec SDD（Story-Driven Development）是一种**结构化需求规范生成方法论**，核心思想：

> **先写规范，再写代码。规范即契约，代码即实现。**

通过 5 个阶段和 4 类标准模板，确保需求从意图到实现的可追溯性。

---

## 核心原则

- **规范优先**：编写任何代码前，必须先阅读并遵循 `openspec/specs/` 中的最新规范。
- **不超范围开发**：仅实现当前变更提案中明确描述的内容，不额外添加未批准的功能。
- **可追溯性**：每一处代码修改都必须对应规范中的具体需求或场景。
- **极简实现**：保持代码简洁易懂，避免过度设计和冗余逻辑。
- **一致性**：严格遵循 `.trae/rules/common-shared-rules.md` 及对应项目共享规则中定义的项目风格、命名规范和架构模式等。
- **默认纯后端**：业务系统变更默认只生成后端产出物和修改后端代码。
- **前端显式授权**：仅当用户明确要求生成或开发前端时，才生成前端规范、前端任务或修改前端代码；不得根据页面描述、接口用途、历史规范或仓库结构推断前端范围。

---

## 工作流规则

### 开始工作前

1. 阅读 `.trae/rules/common-shared-rules.md` 与对应项目共享规则，明确项目上下文、技术栈和约定规范。
2. 加载当前变更提案：通过 `openspec show <变更ID>` 查看完整信息。
3. 逐一审阅提案文件：`proposal.md`（变更原因与范围）、`tasks.md`（实施清单）、`design.md`（技术决策，若有）及增量规范。
4. 检查前端授权：若用户未明确要求前端，确保所有产出物均按纯后端编写，不包含前端规范、任务和代码改动。
5. 验证提案合法性：执行 `openspec validate <变更ID> --strict`，确保无格式或逻辑错误。

### 实施过程中

- 严格按照 `tasks.md` 中的顺序执行任务，不跳步、不遗漏。
- 仅实现清单中列出的功能，不擅自添加额外特性或优化。
- 不修改、重命名无关代码模块，仅聚焦当前变更涉及的范围。
- 代码行为必须与规范中的 `Scenario`（场景）步骤完全匹配，无偏差。

### 完成交付前

- 确认 `tasks.md` 中所有任务均已标记为完成（`- [x]`）。
- 校验代码实现与更新后的规范完全一致，无冲突。
- 重新运行验证命令，确保无新增错误。

## 五阶段工作流

```
阶段 1: 规范生成 ──→ 阶段 2: 审查确认 ──→ 阶段 3: 按规范实施 ──→ 阶段 4: 验证 ──→ 阶段 5: 归档
（不写代码）        （人决策）             （写代码）              （对照检查）      （结束对话前）
```

### 阶段 1：规范生成（不写代码）

**目标**：生成 4 份规划文档，明确意图、方案、标准和任务。

**执行步骤**：

1. 读取项目宪法 `constitution.md`（如存在）
2. 读取项目记忆库上下文（`project-profile.md`、`todo-tracker.md`）
3. 检查是否已有同主题变更目录
4. **使用 AskUserQuestion 询问用户当前需求追踪系统（如 Jira 等）中的需求/任务/BUG 编号和需求名称**
5. **手动创建中文命名变更目录**（见下文「目录与文件命名规范」）
6. 生成规划文档：
   - `proposal.md` — 意图和范围（Intent / Scope / Approach）
   - `design.md` — 技术方案（数据源 / 技术方案 / 接口 / 数据库 / 风险）
   - `specs.md` — 验收标准（Given-When-Then 场景 + 非功能要求）
   - `tasks.md` — 任务清单（只列任务，不执行）
7. **生成「结构性决策确认清单」**（模板见 `assets/decision-checklist-template.md`，源于一次结构性决策未提前确认导致整套产物返工的教训）：把方案中所有**结构性决策**（改一次就要重写全部下游产物的决策）列成待拍板清单，逐条向用户确认，确认结果写回 design.md「决策记录」。最低覆盖：
   - 枚举**复用 vs 独立**（判断依据：两个字段未来值域/文案是否会分叉）
   - 历史数据**处理 vs 不处理**
   - 新增码值是否已做 **测试环境 + 生产环境占用核查**
   - 文案以 **PRD 为准还是以线上存量为准**
8. 向用户汇报规划文档 + 决策确认清单，等待审查确认

**模板文件**：`assets/proposal-template.md`、`assets/design-template.md`、`assets/specs-template.md`、`assets/tasks-template.md`、`assets/decision-checklist-template.md`

### 阶段 2：审查确认（人决策）

**目标**：人工审查规划文档，确认或调整后再进入实施。

**用户输入格式**：
```
我已审查 proposal/design/specs，确认以下调整：
- [调整点 1]
- [调整点 2]

请按以上调整修改规划文档，然后进入实施阶段。
```

### 阶段 3：按规范实施（写代码）

**目标**：按 tasks.md 逐项实现。

**执行约束**：
1. 每次修改文件前，先读取该文件确认上下文
2. 遵循 constitution.md 中的架构约束和编码规范
3. 涉及差异化逻辑时，优先使用 Strategy/Factory 模式，禁止 if-else 判断标识码
4. 修改完成后，添加必要的文档注释和行注释
5. 如需超出 specs.md 范围的改动，先暂停并向用户确认
6. **阶段 3 收尾即时落盘状态快照**（硬性，2026-09-24 新增）：代码完成的**当轮**立即执行，禁止拖到下次会话——
   - 勾选 `tasks.md` 中已完成项；
   - 将 `git status --short` 文件清单 + 完成度快照追加进对话日志（`memory-bank/.../99-dialogue-logs/YYYY-MM-DD_<主题>.md`）。

   **原因**：跨会话摘要可能失真（曾因摘要记录有误导致整轮重复核对），磁盘上的 tasks.md 勾选 + git 快照才是断点续做的唯一可靠依据。成本 1 分钟，省一整轮返工。

### 阶段 4：验证（对照规范检查）

**目标**：逐条验证实现是否符合 specs.md 中的验收标准。

**检查清单**：
- [ ] 功能正确性：是否满足 proposal.md 中的 Intent
- [ ] 范围控制：是否触及 Out of Scope 的内容
- [ ] 架构合规：是否违反 constitution.md 的约束
- [ ] 边界 case：是否处理了 specs.md 中的异常场景
- [ ] 文档同步：项目文档是否需要更新
- [ ] 前端配合：需求涉及前端联调的，按 `frontend-collab-doc` 技能生成前端配合文档（此时阶段 3 已完成、接口契约稳定，信息以真实代码为准）
- [ ] **语言包先行**：涉及枚举文案/多语言的需求，语言包发布（import → CDN → 刷缓存 → 回读抽查）必须先于或同步于代码部署完成，按 `i18n-publish` 技能逐步核对；勿只部署代码不发语言包（2026-09-24 新增）

**输出**：验证报告，标记通过项和未通过项（附原因）。

### 阶段 5：归档（结束对话前必须执行）

**目标**：确保所有变更可追溯，文档同步完成。

**执行步骤**：
1. 确认 tasks.md 全部标记 [x]
2. 将本次变更总结写入对话日志：`memory-bank/.../99-dialogue-logs/YYYY-MM-DD_[主题].md`
3. 如有架构变更，同步更新 `project-profile.md`
4. 更新 `todo-tracker.md`
5. 如有代码变更，按 Git 规范提交

## 规范合规规则

### 需求实现

- 所有使用 **SHALL/MUST** 表述的需求，必须 100% 完整实现。
- 不允许省略、部分实现或修改需求的核心逻辑。

### 场景适配

- 场景必须遵循固定格式：
  ```markdown
  #### Scenario: 场景名称
  - WHEN ...（触发条件）
  - THEN ...（预期结果）
  ```
- 代码行为需覆盖场景中所有 `WHEN` 触发条件和 `THEN` 预期结果，无遗漏。

### 增量处理

- 对于 `ADDED` 类型：按增量规范新增对应的能力或需求实现。
- 对于 `MODIFIED` 类型：基于现有代码修改，确保符合更新后的需求描述。
- 对于 `REMOVED` 类型：彻底移除对应废弃的代码路径，不残留冗余。
- 对于 `RENAMED` 类型：仅修改名称，不改变原有功能逻辑。

---

## 沟通与决策规则

- 遇到疑问时：优先针对规范中的模糊点提问确认，不擅自猜测实现。
- 禁止擅自创造：不凭空新增需求、修改架构或改变技术方案。
- 冲突处理：规范（spec）是"应该是什么"的契约，存量代码是"实际是什么"的事实源——两者冲突时**先以存量代码确认线上真实行为**，再复核规范是否写错/过期：规范错则先反馈再修规范（不自行静默修正），规范对则修改代码或提出新的变更提案；排查/审计类场景一律以代码为准，禁止拿规范推断实际行为（与项目 OpenSpec 规则文档同步修正）
- 问题反馈：发现规范中的歧义、错误或遗漏时，先反馈再实施，不自行修正。

## 目录与文件命名规范

> ⚠️ **本规范为公司级强制要求，所有 OpenSpec 目录和文件命名 MUST 使用中文。**

### `openspec/specs/` 目录命名

- 规范目录名格式：`领域模块名称规范`
- 示例：`供应商合同管理规范`、`合同事件消费规范`

### `openspec/changes/` 目录命名

- 变更目录名格式：`需求编号-需求名称`（需求编号来自需求追踪系统，如 Jira 等）
- 示例：
  - `story-XXX-新增供应商合同管理功能`
  - `task-XXXX-接入三方计价接口`
  - `bug-XXX-修复权限赋值错误`

**创建流程**：

1. 使用 `AskUserQuestion` 工具询问用户：
   - 当前需求/任务/BUG 编号（来自 Jira 等需求追踪系统）
   - 需求名称（中文简要描述，控制在 20 字内）

2. 手动创建目录（**绕过 CLI 命令**）：
   ```powershell
   New-Item -ItemType Directory -Path "openspec/changes/<需求编号>-<需求名称>" -Force
   ```

3. 手动创建文件：
   - `.openspec.yaml`
   - `proposal.md`
   - `design.md`
   - `specs/`（目录）
   - `tasks.md`

4. 参考 `openspec-propose` Skill 的流程生成各制品内容

### 重要约束

- `openspec new change` CLI 命令只接受小写字母+数字+连字符，**不接受中文**。
- 因此创建变更时 **MUST 绕过 CLI 命令**，手动创建中文目录结构。

### 禁止项

| ❌ 禁止 | ✅ 正确 |
|---------|--------|
| 使用英文或拼音作为目录名（如 `integrate-pricing-api`、`gongying-shang`） | `task-XXXX-接入三方计价接口` |
| 使用 `openspec new change` CLI 命令创建变更目录 | 手动创建中文目录 |
| 变更目录名缺少需求编号前缀（如直接命名为 `新增供应商合同管理功能`） | `story-XXX-新增供应商合同管理功能` |

## 快捷指令

| 场景 | 工作流 |
|------|--------|
| 需求明确，直接开干 | 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5 |
| 需求模糊，先调研 | 阶段 1（仅 proposal）→ 人工确认 → 继续 |
| 已有规范，继续实现 | 阶段 3（读取现有 tasks.md，从断点继续） |
| 仅修复 Bug | 跳过阶段 1，直接阶段 3（tasks 只有 1~2 项） |
| 纯文档梳理 | 阶段 1 → 阶段 2 → 阶段 5（无代码） |
| 开发完成，需前端配合联调 | 阶段 3 完成 → 按 `frontend-collab-doc` 生成前端配合文档（阶段 4 期间产出）→ 阶段 5 归档 |

## 使用示例

### 示例 1：新需求开发（完整流程，中文命名）

**用户**：
```
我需要实现 story#12345：业务对象详情页增加扩展字段。

请按 OpenSpec SDD 流程执行。
```

**Kimi**：
1. 读取 `constitution.md` 和项目记忆库
2. 使用 `AskUserQuestion` 确认编号为 `story-12345`，需求名称为 `业务对象详情页增加扩展字段`
3. 创建变更目录 `openspec/changes/story-12345-业务对象详情页增加扩展字段/`
4. 生成 `proposal.md` / `design.md` / `specs.md` / `tasks.md`
5. 汇报文档内容，等待用户审查

**用户审查后**：
```
确认进入实施阶段。
```

**Kimi**：
6. 按 `tasks.md` 逐项实现代码
7. 阶段 4 验证
8. 阶段 5 归档

### 示例 2：已有规范，继续实现

**用户**：
```
继续实现 story-12345-业务对象详情页增加扩展字段，从 tasks.md 的 Task 2 开始。
```

**Kimi**：
1. 读取现有 `openspec/changes/story-12345-业务对象详情页增加扩展字段/tasks.md`
2. 确认 Task 1 已完成，从 Task 2 开始
3. 阶段 3 实施 → 阶段 4 验证 → 阶段 5 归档

## 项目宪法（Constitution）

项目宪法是 OpenSpec 的核心约束文件，定义了项目的技术栈、架构、编码、数据、测试、文档等不可违背的规范。

**创建方式**：
1. 首次使用 OpenSpec 时，基于 `references/constitution-generic.md` 创建项目专属的 `constitution.md`
2. 将 `constitution.md` 放入项目记忆库根目录或 `openspec/` 目录
3. 后续所有需求变更必须遵循宪法约束

**维护原则**：
- 架构变更必须同步更新 `constitution.md`
- 宪法一旦制定，变更需经团队评审
