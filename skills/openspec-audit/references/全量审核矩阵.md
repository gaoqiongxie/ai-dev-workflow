# OpenSpec 全量审核矩阵

首次审核必须逐项检查。复审根据文件变化选择受影响域，但必须验证上下游契约。

## A. 材料与范围

- 需求编号、名称、目标用户和业务价值一致
- PRD、UI、父需求、依赖需求、前后端变更目录齐全
- In Scope、Out of Scope 和依赖边界明确
- 术语、角色、业务对象没有同义混用
- 所有文档版本和文件哈希已记录

## B. 产品与交互

- 列表、新增、编辑、详情、状态切换等页面闭环
- 控件类型、默认值、必填、只读、显隐和联动明确
- 空态、加载、失败、无权限和重复点击有定义
- UI 示例值与业务公式计算结果一致
- 产品限制在前后端都有防绕过设计

## C. 业务规则

- 每条规则有唯一、精确、可测试的定义
- 计算公式定义输入、运算顺序、精度、舍入和异常值
- 汇总指标区分代数和、绝对值和、理论最大值等口径
- 规则冲突时有优先级
- 历史记录、失效数据和引用关系行为明确

## D. 接口契约

- 页面每个动作都有接口或明确复用接口
- 请求 DTO 覆盖页面输入，响应 VO 覆盖页面展示和后续动作
- 字段名称、类型、精度、枚举、必填和长度一致
- 分页、排序、筛选、默认值和最大限制明确
- 错误码、i18n、乐观锁、幂等和重复请求语义明确
- 状态变更后返回值足以更新页面

## E. 数据库

- DDL 与设计字段、实体、DTO、VO 一致
- 所有字段满足 NOT NULL、DEFAULT、类型和注释规范
- 业务长度与数据库长度一致
- 唯一索引与逻辑删除、历史保留不冲突
- 查询条件有适配索引，索引数量符合规范
- 编辑、删除、版本化策略可实际执行
- 初始化、迁移、回滚和历史数据兼容明确
- **提交红线核查（已固化到团队数据库变更审核流程）**
- DDL 与 DML 拆分为独立 SQL 文件（`_ddl.sql`/`_dml.sql`），不混合提交
- SQL 无 `DELETE` 语句（初始化幂等用 `ON DUPLICATE KEY UPDATE`，禁止先删后插）
- DML 首行注明 `-- 预计影响N行`
- DDL 无 `AFTER`/`FIRST`（SQL 审核平台禁改列顺序），无 `ENGINE=InnoDB` 显式声明
- 初始化数据中的环境差异枚举为占位符，未硬编码开发/测试环境参考值

## F. 事务与并发

- 事务边界覆盖完整原子操作
- 分布式锁 key、粒度、获取顺序和释放时点明确
- 锁覆盖事务提交，或有等效数据库约束兜底
- 乐观锁字段从查询到更新形成完整契约
- 新增、编辑、状态切换和重复提交的并发组合已推演
- 超时、锁失败、事务回滚和重试不会产生部分数据

## G. 快照与兼容

- 历史展示依赖的名称、类型、规则是否需要快照
- 快照字段真实存在于 DDL 和实体
- 主数据改名、失效、删除后历史记录可读
- 对外契约变更评估兼容性
- 下游引用使用稳定标识，不依赖可变展示字段

## H. 安全与非功能

- 权限精确到菜单、按钮和后端鉴权
- 输入校验、防注入、敏感数据和审计日志明确
- i18n 无中文硬编码
- 性能指标有口径、数据规模和验证方法
- 日志不泄露敏感信息且支持故障定位

## I. 任务与验收

- tasks 覆盖 proposal、design、API、DDL、前端和测试
- 每个业务规则至少有一个正向和必要的反向场景
- 边界、并发、幂等、失败回滚和权限场景齐全
- Given/When/Then 可直接转为测试用例
- 验收示例与公式、枚举、编号和状态规则一致

## J. 交叉一致性

逐字段比对：

`PRD/UI → proposal → design → API DTO/VO → DDL → 前端规范 → 验收标准`

逐动作比对：

`页面入口 → 接口 → 校验 → 事务/锁 → 数据变化 → 响应 → 页面结果 → 测试断言`

逐状态比对：

`当前状态 → 允许动作 → 目标状态 → 并发限制 → 权限 → 错误结果`

## 完成判定

- 每个适用域必须标记 `checked`
- 不适用域必须标记 `not_applicable` 并说明原因
- 缺少材料标记 `blocked`
- 存在任一 `blocked` 时，结论必须为“审核未完成”
