# OpenSpec 一致性审核

## 目标

一次建立完整审核基线，后续只做差异复审，避免重复报告旧问题，也避免因为审核深度逐轮增加而持续冒出本可首次发现的问题。

审核链路固定为：

`PRD → UI → proposal → design → specs → API → DDL → 前端契约 → tasks → 验收场景`

## 强制原则

1. **首次必须全量审核**：不得只检查用户本轮提到的主题。
2. **复审必须读取基线**：不得脱离上次问题台账重新发散审核。
3. **发现项必须分类**：区分基线遗留、修订引入、首次漏审、范围新增。
4. **旧问题不得重复计数**：同一根因只保留一个稳定问题 ID。
5. **结论必须可追溯**：每个问题都要指出冲突文档、业务动作和验证方式。
6. **文档必须先固定版本**：记录审核时间、文件列表及 SHA-256；审核过程中发生修改则标记版本失效并重新取快照。
7. **不伪造完整性**：缺失 PRD、UI、前端或数据库材料时，明确写入未覆盖范围，不能宣称完成全量审核。

## 审核模式

### 模式 A：首次全量审核

以下任一条件成立时使用：

- 没有 `audit-baseline.json`
- 用户明确要求重新建立审核基线
- 需求范围发生重大变化
- 上次审核材料不完整且本次已补齐

执行步骤：

1. 定位变更目录、PRD、UI、前后端 OpenSpec、父需求和依赖需求。
2. 生成文件清单和 SHA-256 快照。
3. 阅读 `references/全量审核矩阵.md`，逐项完成所有审核域，不得跳项。
4. 建立字段级、动作级、状态级和异常级追踪矩阵。
5. 对 DDL、接口与并发流程做可执行性推演。
6. 对每个发现分配稳定 ID：`AUD-P0-001`、`AUD-P1-001`、`AUD-P2-001`。
7. 输出审核报告和机器可读基线。
8. 只有所有审核域均为 `checked` 或明确为 `not_applicable`，才可给出开发准入结论。

### 模式 B：差异复审

用户说“再次审核”“复审”“验证修订”“是否可以开发”时默认使用：

1. 读取上次 `audit-baseline.json` 和审核报告。
2. 计算当前文件 SHA-256，与基线比较，确定新增、修改、删除文件。
3. 只对以下内容复审：
   - 上次未关闭问题
   - 本次变更触达的审核域
   - 变更影响的上下游契约
   - 修订可能引入的回归点
4. 保持原问题 ID，不得将同一根因改名后作为新问题。
5. 新发现必须标注来源：
   - `revision_introduced`：本次修订引入
   - `scope_added`：需求范围新增
   - `previously_missed`：前次漏审
6. 出现 `previously_missed` 时，必须说明漏审原因，并更新审核矩阵，防止再次遗漏。
7. 报告只呈现“已关闭、仍存在、新增、无法验证”四类变化，不重复全文描述已确认且未变化的内容。

## 完整审核闸门

开始写结论前，逐项确认：

- 产品范围与角色权限
- 页面、状态和交互
- 业务规则与计算口径
- 字段级前后端契约
- 接口请求、响应、错误与幂等
- DDL 字段、索引、逻辑删除与迁移
- 事务、锁、并发和失败恢复
- 历史数据、快照与兼容性
- 安全、i18n、日志和性能
- tasks 与验收场景覆盖
- 跨文档术语、枚举、长度、示例一致性

任一适用项未检查时，结论只能是“审核未完成”，不能给出“可开发”。

## 四类推演

### 字段推演

对每个业务字段追踪：

`UI 控件 → 请求 DTO → 领域对象 → 数据库字段 → 响应 VO → 验收断言`

检查名称、类型、必填、默认值、长度、精度、枚举、只读性和脱敏规则。

### 动作推演

对新增、编辑、删除、失效、生效、查询、导入导出等动作逐一模拟：

`入口 → 参数 → 校验 → 加锁 → 事务 → 数据写入 → 返回 → 页面刷新 → 重试`

### 状态推演

列出每个状态及允许转换，检查按钮权限、后端防绕过、同状态请求和非法转换。

### 故障推演

至少覆盖：并发请求、重复提交、超时重试、锁失败、乐观锁冲突、部分写入、依赖数据变化、表达式编译失败和历史数据读取。

## 问题去重规则

问题指纹由以下内容组成：

`业务对象 + 业务动作 + 根因 + 受影响契约`

满足以下任一情况时视为同一问题：

- 表述不同但根因相同
- 一个问题是另一个问题的直接表现
- 多份文档同时缺失同一个契约字段

复审时更新原记录的状态、证据和修订说明，不创建新 ID。

## 分级规则

| 等级 | 定义 | 准入影响 |
|---|---|---|
| P0 | 无法实现、会产生错误数据、并发破坏唯一性、关键契约断裂 | 阻止开发 |
| P1 | 行为存在歧义、主要测试场景缺失、较高返工风险 | 原则上修订后开发 |
| P2 | 文案、示例、可维护性或低风险边界问题 | 可带项开发 |

不要因为数量多而提高等级，也不要把所有建议都列为问题。

## 基线文件

默认保存在变更目录：

- `audit/audit-baseline.json`
- `audit/audit-report.md` 或用户指定的 HTML 报告

`audit-baseline.json` 必须符合 `templates/audit-baseline.schema.json` 的字段结构，至少包含：

- 需求标识和审核模式
- 文件路径、哈希和审核时间
- 审核域覆盖状态
- 稳定问题 ID、指纹、等级、状态和证据
- 未覆盖材料与剩余风险
- 最终准入结论

如果用户只要求查看结果、不希望修改需求目录，可将产物输出到工作区交付目录，但复审时必须定位并读取该基线。

## 报告结构

首次审核报告：

1. 审核结论
2. 审核材料与版本
3. 覆盖矩阵
4. P0/P1/P2 问题台账
5. 跨文档追踪矩阵
6. 测试缺口
7. 开发准入条件
8. 未覆盖范围

差异复审报告：

1. 复审结论
2. 文件变化摘要
3. 已关闭问题
4. 仍存在问题
5. 修订引入问题
6. 前次漏审问题及原因
7. 当前准入条件

## 最终结论

只允许以下结论：

- `审核未完成`：适用审核域未全部覆盖或关键材料缺失
- `不准入`：存在 P0
- `有条件准入`：无 P0，但存在需开发前明确的 P1
- `准入`：无 P0，P1 已关闭或被负责人明确接受

不得用模糊表述代替结论。

## 与其他 Skill 的关系

- 本 Skill 审核“规范是否足以开发”。
- 项目的规格校验 Skill（如 `spec-verify`）审核“实现是否符合规范”。
- 涉及数据库时必须同时读取项目数据库规范。
- 涉及 i18n 时调用对应项目 i18n Skill，不自行猜测 key。
- 用户要求正式可视化报告时，再调用 `html-report` 生成 HTML；审核事实和基线仍由本 Skill 维护。
