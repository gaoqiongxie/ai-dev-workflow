# OpenSpec 存量业务规格基线初始化

为存量业务代码初始化OpenSpec真相源规格文档，通过分析Controller→Service实现链路，建立业务模块的基线规格。

## 1. 核心原则

- **规范优先**：规格文档是AI辅助开发的"真相源"，必须准确反映业务逻辑。
- **可追溯性**：每个需求必须对应具体的Controller接口和Service实现。
- **完整性**：所有Controller接口都必须有对应的Requirement覆盖。
- **精确性**：使用MUST/SHALL关键词锁定业务意图，避免歧义。
- **中文命名**：所有目录和文件命名MUST使用中文。

## 3. 目录与命名规则

### 3.1 目录结构

```
openspec/
└── specs/
    ├── 资产处置单规范/
    │   └── spec.md
    ├── 订单管理规范/
    │   └── spec.md
    └── 支付处理规范/
        └── spec.md
```

### 3.2 命名规则（MUST遵循）

- 规范目录名格式：`领域模块名称规范`（如：供应商合同管理规范、合同事件消费规范）
- **禁止**使用英文或拼音作为目录名
- **禁止**缺少"规范"后缀（如直接命名为"资产处置单"而非"资产处置单规范"）

---

## 4. 模块粒度原则

### 4.1 核心原则

以"可独立变更的业务模块"为单位，每个规格文件聚焦一个相对完整、用户可感知的功能领域。

### 4.2 合适的粒度

- 同一业务领域的多个Controller共同构成1个模块规范（如：OrderController + OrderQueryController → 订单管理规范）
- 一个Controller提供了一组某个模块相关"业务能力"的接口 = 1个模块规范
- 管理同一业务实体生命周期的相关接口 = 1个模块规范

### 4.3 避免

- 过粗："所有订单相关功能"（跨多个业务领域）
- 过细："单个接口"（缺乏业务上下文）

### 4.4 按领域分组示例

同一模块可能包含多个Controller，按业务领域归组：

| 领域 | Controller | 业务能力 |
| --- | --- | --- |
| 订单管理 | OrderController, OrderQueryController | 订单创建、查询、取消 |
| 支付 | PaymentController, PaymentCallbackController | 支付发起、回调、退款 |
| 资产处置 | AssetDisposalController, AssetDisposalAuditController | 资产处置单全生命周期 |

## 5. 探索模块实现

使用 `openspec-explore` 技能分析选定的模块：

```
使用openspec-explore技能，分析AssetDisposalController和AssetDisposalAuditController及其Service层实现。
需要理解创建基线规格所需的业务逻辑。
```

### 5.1 追踪调用链

对模块中每个Controller的每个接口，追踪：

```
Controller方法
       │
       ▼
Service接口
       │
       ▼
ServiceImpl（实际逻辑）
       │
       ├── 核心业务逻辑
       ├── 状态机转换
       ├── 校验规则
       ├── 异常处理
       └── 外部依赖
```

### 5.2 捕获关键实现细节

为场景覆盖记录以下内容：

1. **核心业务逻辑**：主流程执行路径
2. **状态机转换**：实体状态变更
3. **边界条件**：输入校验、限制条件
4. **异常处理**：错误场景和恢复机制
5. **并发控制**：锁、事务、幂等性

## 6. 编写spec.md

### 6.1 标准模板

参见 [references/spec-template.md](references/spec-template.md) 获取完整模板。

**快速参考：**

```markdown
# [模块名称]规范

## 目的

[业务价值描述，不少于50字符，说明该能力解决了什么问题、带来了什么价值]

## 需求

### Requirement: [需求名称]

系统SHALL/MUST [具体行为描述].

#### 场景: [场景名称]

- **假设** [前置条件]
- **当** [触发动作]
- **那么** [预期结果]
```

### 6.2 需求与场景的对应关系

- 每份spec.md对应一个业务模块，该模块可能包含一个或多个Controller
- 每个**需求**对应一个Controller接口背后的Service层impl的具体实现
- Service层impl中的所有关键逻辑用该需求下的多个**场景**来覆盖
- 场景必须嵌套在每个 `### Requirement:` 之下，不单独设立章节
- 一个需求至少要有核心业务逻辑的场景覆盖

### 6.3 场景覆盖矩阵

| Service逻辑类型 | 最低场景数 |
| --- | --- |
| 简单CRUD | 1（主流程） |
| 校验逻辑 | 2（有效+无效） |
| 状态转换 | 每个转换1个 |
| 异常处理 | 每种错误类型1个 |
| 并发控制 | 1（幂等/锁） |

## 7. 规范合规规则

### 7.1 需求编写

**使用强制关键词：**

- `SHALL` — 系统必须做某事
- `MUST` — 强制要求
- `MUST NOT` — 禁止行为

**示例：**

```markdown
### Requirement: 创建处置单

系统SHALL基于用户提交的处置请求创建新的资产处置单，并校验资产状态和处置原因。
处置单状态MUST在创建时初始化为"草稿"。
系统MUST NOT允许为已在处置流程中的资产创建处置单。
```

### 7.2 场景编写

**结构：假设 → 当 → 那么**

```markdown
#### 场景: 成功创建可用资产的处置单

- **假设** 用户拥有创建处置单的权限
- **并且** 资产ID"ASSET-001"存在且状态为"可用"
- **并且** 资产"ASSET-001"不存在进行中的处置单
- **当** 用户提交处置单创建请求：
  | assetId | ASSET-001 |
  | reason  | 损坏报废   |
- **那么** 系统SHALL创建新的处置单
- **并且** 处置单状态SHALL为"草稿"
- **并且** 创建的处置单SHALL关联到该资产
```

### 7.3 编写注意事项

- 需求定义系统必须做的某件事，场景通过具体例子验证需求的正确性
- 使用精确的业务语言，避免模棱两可的词汇（如"大概"、"可能"、"差不多"）
- 通过MUST/SHALL关键词锁定业务意图，防止AI在开发过程中自由发挥
- 每个场景应可独立验证
- **假设**设定前置条件，**当**触发动作，**那么**断言结果

## 8. 验证完整性

### 8.1 检查清单

- [ ] 模块中所有Controller的所有接口都有对应的Requirement
- [ ] 每个Requirement至少有一个场景（核心逻辑）
- [ ] 复杂Service逻辑有多个场景覆盖：
  - [ ] 主流程
  - [ ] 异常场景
  - [ ] 边界条件
- [ ] 所有场景使用 **假设**/**当**/**那么** 结构
- [ ] Requirement使用SHALL/MUST关键词
- [ ] 目录命名使用中文且以"规范"结尾

### 8.2 格式验证

完成检查清单后，MUST使用 `openspec-cn` 工具验证规范格式的正确性：

```bash
openspec-cn validate "XXX规范" --type spec --strict --json 2>&1
```

- `"XXX规范"` 替换为实际的规范目录名称（如 `"资产处置单规范"`）
- `--type spec` 指定验证类型为规格文档
- `--strict` 启用严格模式，确保所有格式规则都被检查
- `--json` 以JSON格式输出验证结果，便于解析
- `2>&1` 合并标准错误和标准输出

**验证通过标准：** 命令执行后无错误输出，或所有错误均已修复至验证通过。
