# spec.md 模板

OpenSpec基线规格文档的完整模板。

---

```markdown
# [业务能力名称]

## 目的

[业务价值描述]

阐述该业务能力为系统解决了什么问题、带来了什么价值。
推荐长度不少于50个字符，帮助AI理解需求的业务背景。

## 需求

### Requirement: [需求名称1]

系统SHALL [具体行为描述].
系统MUST [强制约束].

#### 场景: [场景名称 - 如：核心流程成功]

- **假设** [前置条件1]
- **并且** [前置条件2]
- **当** [触发动作]
- **那么** [预期结果1]
- **并且** [预期结果2]

#### 场景: [场景名称 - 如：异常情况]

- **假设** [前置条件]
- **当** [触发动作 - 异常输入或异常状态]
- **那么** [预期结果 - 错误处理行为]

### Requirement: [需求名称2]

系统SHALL [具体行为描述].

#### 场景: [场景名称]

- **假设** [前置条件]
- **当** [触发动作]
- **那么** [预期结果]
```

---

## 各章节编写指南

### 标题（一级标题）

- 使用 `#` 标题
- 简明的业务能力名称
- 示例：`# 用户认证`、`# 资产处置单管理`、`# 支付模块`

### 目的

- 描述业务价值和解决的问题
- 不少于50个字符
- 帮助AI理解业务背景
- 聚焦"为什么"而非"怎么做"

### 需求

- 使用 `## 需求` 作为章节标题
- 每个需求使用 `### Requirement: [名称]`
- 必须包含 `SHALL` 或 `MUST` 关键词
- 一个需求对应一个Controller接口背后的Service层impl实现
- 描述行为契约，而非实现细节

### 场景

- 嵌套在每个 `### Requirement:` 之下
- 使用 `#### 场景: [名称]`
- 必须使用 **假设**/**当**/**那么** 结构
- 一个需求可以有多个场景
- 使用 **并且** 补充条件/结果

#### 场景覆盖优先级

1. **核心业务逻辑**（必须有）— 主流程
2. **状态机转换**（应该有）— 状态变更
3. **边界条件**（应该有）— 输入校验
4. **异常处理**（应该有）— 错误场景
5. **并发控制**（可以有）— 锁、幂等

#### 编写规则

- 使用精确的业务语言
- 避免模棱两可的词汇（"大概"、"可能"、"差不多"）
- 用MUST/SHALL关键词锁定业务意图
- 每个场景应可独立验证
- **假设**设定前置条件，**当**触发动作，**那么**断言结果
