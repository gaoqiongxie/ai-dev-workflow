# 执行路由

按用户意图和当前材料确定唯一入口，避免重复生成文档或跨门禁实施。

| 用户意图 | 当前条件 | 动作 | 预期状态 |
|---|---|---|---|
| 新需求、需求补充、较大 Bug | 尚无完整 OpenSpec | 执行 Gate 1，随后调用 `openspec-propose` 或项目规定的 OpenSpec 流程 | `可设计` 或 `待澄清` |
| 文档已完成、是否可开发 | 无审核基线 | 执行 Gate 2，并调用 `openspec-audit` 首次全量审核 | `文档准入` 或 `文档待审` |
| 再次审核、验证修订 | 已有审核基线 | 调用 `openspec-audit` 差异复审，不重新全量发散 | 保持或进入 `文档准入` |
| 开始开发、继续开发 | 已文档准入 | 执行 Gate 3，调用 `openspec-apply-change` 按切片实施 | `实施中` |
| 开始开发、继续开发 | 未文档准入 | 停止编码，列出缺失门禁证据 | 原状态 |
| 编码完成、检查代码 | 主体实现已完成 | 先确认 `tasks.md` 与规范映射，再执行 Gate 4 | `编码完成` 或 `提测准入` |
| 可以提测吗 | 有完整构建与测试条件 | 执行 Gate 4，不以代码浏览代替构建和测试 | `提测准入` 或 `不准入提测` |
| 实施中改变 API/DDL/公式/状态机 | 核心契约变化 | 暂停实现，更新 OpenSpec，执行受影响域差异复审 | 回到 `文档待审` |
| 仅修局部实现缺陷 | 不改变规范 | 留在 Gate 3，重跑相关验证 | `实施中` 或 `编码完成` |

## 调用顺序

1. 读取项目规则、变更目录、`tasks.md`、门禁记录和审核基线。
2. 判断当前状态和本轮唯一门禁。
3. 加载对应专项 Skill，不同时启动多个相互重叠的研发流程。
4. 执行检查或实施，并保存可复现证据。
5. 更新原门禁记录和原问题 ID。
6. 只给出当前门禁允许的下一步。

## 禁止路由

- 未通过 Gate 1 时直接生成看似完整的技术方案。
- 未通过 Gate 2 时调用实现流程写业务代码。
- 将“代码已写完”直接等同于“提测准入”。
- 复审时忽略基线，重新创建一套问题编号。
- 代码已改变核心契约但只改实现、不回写 OpenSpec。
- 环境阻塞时宣称测试通过。
