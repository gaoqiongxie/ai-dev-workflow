# 低返工研发门禁

## 目标

减少“生成文档 → 反复审核 → 编码 → 再次发现核心问题”的缺陷性返工。允许必要的探索性调整，但要求核心约束在编码前冻结、问题在最早可发现阶段暴露、后续审核只验证差异。

本 Skill 是研发全生命周期的**编排层**，不替代现有能力：

- `openspec-sdd` / `openspec-propose`：生成规范。
- `openspec-audit`：规范全量审核与差异复审。
- `openspec-apply-change`：按任务实现。
- 项目 i18n、CRUD、Excel 等 Skill：处理专项实现。

开始执行前必须读取：

- `references/执行路由.md`：根据用户意图与当前状态选择唯一工作流。
- `references/门禁检查清单.md`：逐项检查当前门禁，不凭印象给结论。
- `references/门禁记录模板.md`：维护同一份门禁状态和证据台账。

## 触发场景

以下情况必须调用：

- 新需求或较大 Bug 准备进入 OpenSpec。
- 用户要求开始开发、继续开发或按文档实施。
- 用户表示“文档已完成”“编码已完成”“可以提测吗”。
- 同一需求已经出现两轮以上审核或修复。
- 实施过程中发现需要修改核心接口、DDL、状态机、计算口径或并发方案。

简单文案调整、纯查询、无业务行为变化的机械修改可以不调用。

## 核心原则

1. **完成不等于准入**：文档准入、编码完成、提测准入、发布准入必须分开表述。
2. **问题前移**：在最早能验证的阶段执行检查，不把编译、契约、权限、并发留到最后。
3. **证据优先**：没有检查结果或测试证据，不得宣称通过。
4. **门禁失败即暂停**：不能靠“后续再补”跨过 P0 或未决核心 P1。
5. **一次全审，后续差审**：首次规范审核必须全量，后续只审基线遗留、变更影响和回归点。
6. **同根因不重复**：问题使用稳定 ID；修复后更新状态，不换名称重新计数。
7. **切片交付**：按可独立验收的纵向切片实施，每片完成立即验证。
8. **范围变化重新过门**：新增范围或核心口径变化时，回到对应门禁，不在代码中偷偷定义需求。
9. **验证先于完成**（借鉴 superpowers verification-before-completion）：宣称任何"完成 / 修复 / 通过"之前，必须实际运行验证命令或复现验证场景拿到结果；修复类宣称必须先复现原始问题场景，再验证修复后场景，不得用"应该没问题""已自测"代替证据。
10. **最小实现**（借鉴 ponytail "最懒资深开发"）：编码前先问"这个功能 / 字段 / 分支 / 配置项真的必要吗"；能用现有机制（已有接口、配置、枚举、通用逻辑）解决就不新增代码；拒绝"以防万一"的抽象层、预留参数和过度设计；每段新增代码都必须能说出一个它无法被现有实现替代的业务场景，说不出就不写。
11. **结论先行**（借鉴 i-have-adhd）：所有门禁输出先说结论状态和唯一合法下一步，再给依据和证据；多步骤检查项必须编号列出、逐项给出状态；不把关键结论埋在背景铺垫和过程描述里；一次输出只推进一个门禁动作。

## 状态模型

只允许使用以下研发状态：

| 状态 | 含义 | 允许下一步 |
|---|---|---|
| `待澄清` | 核心业务决策或材料缺失 | 补齐范围 |
| `可设计` | 范围与业务约束已冻结 | 编写 OpenSpec |
| `文档待审` | 规范已生成，尚未全量审核 | 执行规范审核 |
| `文档准入` | 无 P0，核心 P1 已关闭或接受 | 开始编码 |
| `实施中` | 按验收切片开发与验证 | 继续实施 |
| `编码完成` | 主体代码完成，但尚未满足提测证据 | 执行提测门禁 |
| `提测准入` | 构建、静态检查、联调和关键测试通过 | 提交测试 |
| `发布准入` | 发布、迁移、监控和回滚准备完成 | 发布 |

禁止只说“已完成”或“已准入”，必须说明具体状态。

## 启动协议

每次调用按以下顺序执行：

1. 定位项目规则、OpenSpec 变更目录、`tasks.md`、`gate/gate-status.md` 和 `audit/audit-baseline.json`。
2. 如果门禁记录不存在，根据现有材料推断最低可信状态并创建记录；不得把用户口头的“完成”直接作为通过证据。
3. 按 `references/执行路由.md` 确定本轮唯一门禁。
4. 读取 `references/门禁检查清单.md` 中当前门禁及项目专项项。
5. 加载本轮需要的专项 Skill，执行检查、审核或实施。
6. 将结果、命令、测试和阻断问题写入同一份门禁记录。
7. 只报告当前状态、门禁结论、证据和一个合法下一步。

材料不完整时做可执行的缺口检查并标记 `BLOCKED`，不得伪造通过，也不得重复创建另一份状态台账。

## 四道门禁

### Gate 1：范围门

**目标**：确认正在解决什么，不解决什么。

必须具备：

- 需求编号、名称、PRD、UI、父需求和依赖材料。
- In Scope、Out of Scope、角色与权限。
- 业务动作、状态、核心计算口径、唯一性口径。
- 数据规模、分页方式、历史数据和兼容范围。
- 未决事项清单，每项包含负责人和决策状态。

必须执行四类问题扫描：

- 角色：谁查看、谁操作、谁审批、后端如何防绕过。
- 动作：新增、编辑、删除、生效、失效、查询、导入导出。
- 状态：允许转换、重复请求、非法转换、终态。
- 边界：空值、上限、并发、超时、重试、依赖变化。
- 必要性：每项 In Scope 功能必须能回答"不做的业务代价是什么"；答不出或可用现有机制替代的，移出范围或降级为配置项（对应核心原则 10）。

**通过条件**：无未决核心业务口径；材料缺失已明确标记且不影响设计。

**失败结论**：`待澄清`。不得生成完整技术方案或开始编码。

### Gate 2：设计门

**目标**：证明规范足以指导编码。

必须建立四张追踪矩阵：

#### 字段矩阵

`UI 控件 → 请求 DTO → 校验 → 领域对象 → DB 字段 → 响应 VO → 页面展示 → 测试断言`

检查名称、类型、必填、默认值、长度、精度、枚举、只读、脱敏和 i18n。

#### 动作矩阵

`入口 → 参数 → 权限 → 校验 → 锁/幂等 → 事务 → 数据写入 → 返回 → 刷新 → 重试`

#### 状态矩阵

记录当前状态、目标状态、允许角色、前端按钮、后端校验、同状态结果、非法转换错误码。

#### 故障矩阵

至少覆盖并发请求、重复提交、锁失败或过期、乐观锁冲突、超时重试、部分写入、依赖数据变化和历史数据读取。

每项关键设计必须改写为“声明 + 证据”：

| 设计声明 | 验证方式 |
|---|---|
| 同维度只有一个有效对象 | 并发集成测试最终仅一条有效记录 |
| 锁覆盖完整事务 | 调用边界检查与超时用例 |
| 错误码可被前端消费 | 契约样例回放 |
| 分页候选完整可选 | 超过单页规模的验收用例 |

随后调用 `openspec-audit` 执行首次全量审核。

**通过条件**：

- 适用审核域均已覆盖。
- 无 P0。
- 核心 P1 已修订或由负责人明确接受。
- `proposal/design/specs/API/DDL/tasks/验收场景` 交叉一致。
- 已生成审核基线和文件哈希。

**失败结论**：`文档待审`。不得进入实现。

### Gate 3：实施门

**目标**：避免一次生成全部代码后集中返工。

实施前读取审核基线和全部未关闭问题。使用 `openspec-apply-change` 按可验收切片执行，推荐顺序：

1. DDL、Entity、Mapper。
2. DTO、VO、接口契约。
3. 核心新增/编辑流程。
4. 状态切换、幂等与并发。
5. 前端列表与查询。
6. 前端详情与业务计算。
7. 权限、i18n、错误态、空态。
8. 联调、边界和故障测试。

每个切片必须在进入下一片前完成：

- 代码与规范映射检查。
- 相关编译或静态检查。
- 该切片的正常、异常和边界测试。
- **验证先于完成**：宣称本切片完成前，实际运行上述检查/测试命令并记录真实输出；修复类任务先复现原缺陷场景，再验证修复后场景。
- 更新 `tasks.md` 的完成状态和验证证据。
- 检查是否影响字段、动作、状态或故障矩阵。

若实施揭示设计问题：

1. 暂停编码。
2. 标记问题来源：`implementation_discovered`。
3. 更新对应 OpenSpec 和追踪矩阵。
4. 调用 `openspec-audit` 做受影响域的差异复审。
5. 通过后继续，不允许仅修改代码绕过规范。

**通过条件**：所有实施任务完成，每项都有验证证据，无未同步设计变化。

**阶段结论**：`编码完成`，但不得直接宣称 `提测准入`。

### Gate 4：提测门

**目标**：证明实现满足规范和工程质量要求。

#### 两阶段审查（借鉴 superpowers two-phase review）

进入提测门前，必须分别执行两个阶段，且两个阶段独立出具结论，不得合并为一次"看起来没问题"的审查：

**阶段一：规格符合性审查**

只回答一个问题：实现是否兑现了规范承诺？

- 对照 OpenSpec `proposal / design / specs / API / DDL / tasks / 验收场景` 逐项核对实现。
- 字段、动作、状态机、错误码、分页结构、权限点与规范的一致性。
- 验收场景（AC）逐条回放，标注：通过 / 未实现 / 实现偏离。
- 输出按严重度分级的问题清单（critical 阻断提测）。

**阶段二：代码质量审查**

只回答一个问题：代码本身是否达标？

- 命名、结构、分层职责、模式使用、圈复杂度、重复代码。
- 安全（注入、越权、敏感信息）、性能（N+1、批量缺失）、日志与异常处理。
- 规范符合性（项目编码规范、i18n、禁止项）。

阶段一发现 critical 问题时，先修复并复审规格符合性，再进入阶段二；不得用代码写得不错为由绕过规格偏离。

#### 常规检查项

根据项目实际技术栈执行并记录：

- 后端聚合编译、目标单测和必要集成测试。
- 前端 build、lint、类型或语法检查。
- `git diff --check`。
- API 请求、响应、分页、错误码、幂等联调。
- 权限、i18n、日志、安全和数据隔离检查。
- 并发、超时、重试、上限和历史兼容场景。
- `tasks.md`、验收标准与实现的逐项映射。
- 当前文件哈希与审核基线一致性。

失败项必须区分：

- `implementation_defect`：实现偏离规范。
- `revision_introduced`：本次修改引入。
- `previously_missed`：前置门禁漏审。
- `environment_blocked`：环境导致无法验证。

出现 `previously_missed` 时，必须更新本 Skill 对应检查表或项目专项规则，不能只修当前代码。

**通过条件**：

- 两阶段审查均已完成且阶段一无 critical 问题。
- 无 P0。
- 无未接受的提测阻断 P1。
- 构建和静态检查通过。
- 关键联调、并发和边界场景有成功证据。
- 无无法解释的未验证项。

**最终结论**只允许：

- `审核未完成`
- `不准入提测`
- `有条件提测准入`
- `提测准入`

## 验证证据格式

`tasks.md` 中每个任务应包含或关联：

```markdown
- [x] 实现评分模型状态切换
  - 规范：AC-08、后端接口规范 4.3
  - 影响：状态矩阵 S2，接口 `/api/score-model/status`
  - 验证：`mvn -Dtest=ScoreModelStatusTest test`
  - 结果：通过，3 个用例
  - 证据时间：YYYY-MM-DD HH:mm
```

不能用“已自测”“应该没问题”“代码已完成”代替证据。

## 变更影响规则

修改以下任一内容时，必须回到 Gate 2 做受影响域差异复审：

- 核心计算公式或业务口径。
- API 路径、字段、枚举、错误码或分页结构。
- DDL 字段、索引、唯一性或删除策略。
- 状态机、权限、事务、锁、幂等和重试方案。
- 数据来源、历史兼容或快照方案。

仅局部实现修正且不改变规范时，可留在 Gate 3，但必须重新运行相关验证。

## 审核去重与反馈

问题指纹：

`业务对象 + 业务动作 + 根因 + 受影响契约`

同一指纹始终复用原问题 ID。每次复审只输出：

- 已关闭
- 仍存在
- 修订引入
- 范围新增
- 前次漏审
- 无法验证

`previously_missed` 必须记录漏审原因，并落实为以下至少一项：

- 更新通用审核矩阵。
- 更新项目规则。
- 增加自动检查。
- 增加测试模板。

## 门禁记录

默认在 OpenSpec 变更目录维护 `gate/gate-status.md`，格式见 `references/门禁记录模板.md`。

- 首次执行创建，后续更新原文件。
- `audit/audit-baseline.json` 继续由 `openspec-audit` 管理，门禁记录只引用它，不复制问题台账。
- 未要求创建 OpenSpec 或用户仅咨询方法时，可以只在对话中输出，不创建项目文件。
- 记录中的证据必须可复现，命令失败、环境缺失和材料缺失分别如实记录。

## 输出格式

每次执行输出以下摘要：

```markdown
## 当前阶段
- 需求：<编号与名称>
- 当前状态：<状态>
- 当前门禁：Gate N

## 门禁结果
- 结论：通过 / 不通过 / 未完成
- 已验证：<证据摘要>
- 阻断项：<稳定问题 ID>
- 未验证：<原因>

## 下一步
- 只列允许执行的下一步，不跨门禁。
```

## 与项目规则的关系

- 优先遵守项目共享规则文件（如 `AGENTS.md`、`.trae/rules/` 或 `.claude/` 下的项目规则）、数据库规范。
- 新需求、Bug 和继续开发仍按项目规定的 OpenSpec 流程执行。
- 涉及 i18n 时必须调用项目对应 i18n Skill。
- 涉及数据库时必须读取项目数据库规范。
- 不自动执行 Git 提交或推送，必须等待用户明确授权。
- 对话结束前按项目规则归档任务追踪和对话日志。

## 成效指标

持续统计：

- 首次全量审核后新增 P0 数量，目标为 0。
- `previously_missed` 数量及来源。
- 编码后核心契约变更次数。
- 提测阶段首次发现的基础问题数量。
- 同一根因重复出现次数。
- 自动门禁覆盖率。

目标不是零修改，而是：首次全量审核后不再出现新 P0、编码阶段不再重新定义核心契约、提测阶段不再首次发现基础问题。
